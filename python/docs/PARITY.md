# Java → Python parity

Status as of 2026-10-27. Verified by inventorying both trees, not by recollection.

## The headline

**The Python port is not at feature parity, and is not close.**

```
Java production code   32,076 lines   90 classes   26 UI screens
Python port             2,006 lines   11 modules    0 UI screens
```

About **6%** by volume. What exists is the scientific core, chosen because it is the
part that must be numerically exact and the part everything else depends on. The
application around it — the screens, the procedure runner, patient records, the results
map — is not written.

Anyone reading this to decide whether the Python can run a session: **it cannot.** It
has no window flow, no way to enter a participant, and no way to save a result.

## Two gaps that were not just "unwritten" — both now closed

These were places where the Python **looked** finished and was not. Both were found by
this audit, not by the tests, because the tests only check what was written. Both were
small, so they were fixed rather than listed.

### 1. Perimetric dB was absent — FIXED

`Functions.decibelsValue` computes `10*log10(maxLuminance / stimulusLuminance)` — the
number in `session_data.txt` and on the results map colourbar.

The Python had only `core/ladder.contrast_db`, which is `-20*log10(Michelson)`.
**These are different quantities with the same unit name**, so the port could not have
produced the dB column at all — and nothing in the tests noticed, because nothing yet
writes a session file.

`ladder.perimetric_db()` now exists and is pinned: `perimetric_db(214.67, 3.26103)`
returns **18.18**, which is the colourbar maximum on the real Java results screen. The
`backgroundLuminance` argument the Java accepts and ignores is omitted rather than
accepted and ignored.

### 2. `geometry.py` was the flat model only — FIXED

Java has **two** geometry implementations:

- `Functions.pxForOneDg(resolution, field)` — flat, one scale everywhere
- `ScreenGeometry.localPixelsPerDegreeX(eccentricity)` — `pxPerMm · distance · (π/180) / cos²(e)`

The Python port had only the flat one. `PhysicalScreen` now provides the spherical
model, built from measured millimetres and a viewing distance rather than a stated
field, with `flat_geometry()` to derive the approximation for comparison. The
correction, now pinned by tests:

| eccentricity | factor | error if ignored |
|---|---|---|
| 5° | 1.00765 | +0.77% |
| 10° | 1.03109 | +3.11% |
| 20° | 1.13247 | **+13.25%** |
| 30° | 1.33333 | **+33.33%** |

At the proposal's ±5° locations this is 0.77% — below measurement noise. For any
wider-field mapping it is not: a patch sized with the centre scale at 20° is 13% wrong.

Still open: Specvis exposes a **"Sphericity correction" on/off setting**, and the
procedure must honour it when the runner is written. Having both models available is
not the same as wiring the choice through.

## What parity would actually require

Roughly in dependency order:

1. ~~Perimetric dB and the spherical geometry~~ — **done**, 2026-10-27.
2. **Settings and data model** — patient, luminance scale, stimulus, session. Needed by everything.
3. **The procedure runner** — the trial loop against the backend seam. The 6,201 Java lines are four near-identical classes; one parameterised runner should replace them.
4. **Session output** — `session_info.txt`, `session_data.txt`, the logs. This is where parity becomes checkable against real Java sessions.
5. **The PyQt6 screens** — the largest block by volume, the least scientifically risky.
6. **Results map** — `Contour2DMap` is 3,036 lines, but `IsoCell` is 2,624 of those and is a generated lookup table; matplotlib's `contourf` replaces most of it.
7. **Behavioural mode and the unseen-discrimination analysis.**

### The acceptance test to aim for

The Java can replay a real recorded session: `PilotReplayCheck` reproduces
`R_20261024_KTn0` exactly. **The Python port should be held to the same bar** — feed it
the same answer sequence and require byte-identical `session_data.txt`. Until that
passes, "ported" means "the arithmetic agrees", not "the program agrees".
